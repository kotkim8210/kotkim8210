## 왜 이 순서인가 (Stage-Gate)

대부분의 1인 창업이 죽는 지점은 "만들기"가 아니라 **"안 팔리는 걸 만들기"**입니다.
그래서 각 단계마다 **통과(GO)/탈락(KILL) 기준**을 두고, 통과한 것만 다음 단계로 넘깁니다.

| 단계 | 활동 | 통과(GO) | 탈락(KILL) | 사용 도구 |
|---|---|---|---|---|
| 0. 문제 선별 | 페인 후보 10개 점수화 | 상위 2~3개 압축 | "이미 잘 풀린 문제" 제거 | **Tool 01** |
| 1. 수요 검증 | 랜딩+가짜버튼, 개발 0줄 | CTA 클릭률 ≥ 합격선 + 등록 N건 | 합격선 미달 → 즉시 폐기 | **Tool 02 → 03** |
| 2. 선판매 검증 | 베타 유료 슬롯/사전결제 | 실제 결제자 ≥ X명 | 무료엔 몰려도 결제 0 | **Tool 03** |
| 3. 최소 제품 | 결제 고객용 핵심기능만 AI로 빌드 | 재방문/리텐션 유지 | 리텐션 붕괴 | **Tool 03** |
| 4. 운영·확장 | 반복작업만 자동화, 판단은 사람 | LTV:CAC ≥ 3 | 단위경제 역전 | **Tool 03** |

## 도구 구성

### 🏠 `index.html` — 허브
세 도구로 연결되는 시작 페이지 + 전체 흐름 요약.

### 📊 Tool 01 — `pain-scorer.html` · 페인포인트 점수화 시트
레딧·커뮤니티에서 모은 고객 불편을 네 축으로 점수화(1~5)해 우선순위를 매깁니다.

- **빈도 × 강도 × 지불가능성 × 경쟁공백** (가중치 조절 가능, 기본은 지불가능성·경쟁공백에 가중)
- 점수 ≥ 3.8 → `GO`, 3.0~3.8 → `WATCH`, < 3.0 → `KILL`
- **지불 의향 증거(인용·링크)** 칸이 비면 −0.3 페널티 → 추측 방지
- CSV 내보내기, localStorage 자동 저장
- ⚠️ 주의: *레딧에서 불평하는 사람 ≠ 돈 내는 사람.* 그래서 "지불가능성" 축과 "증거" 칸이 핵심입니다.

### 🚪 Tool 02 — `validation-landing.html` · 검증용 랜딩 + 가짜 결제버튼
**개발 0줄**로 수요를 테스트하는 스모크 테스트(가짜 문) 페이지.

- 모든 문구를 **클릭해서 바로 수정**(contenteditable, localStorage 저장)
- 가격 3종 선택 + **사전 예약 버튼** → 이메일 캡처 모달. "유료 결제 의향" 체크는 *말로 한 약속(약한 신호)*, 등록 후 뜨는 **예약금 결제(2단계)가 진짜 강한 신호(돈)**
- **퍼널 자동 추적**: 방문 → 50% 스크롤 → CTA 클릭 → 이메일 등록 → 유료 의향(약) → **예약금 결제 클릭(강)**
- 우측 하단 **📊 실시간 미니 대시보드**(CTR/전환율/퍼널 막대/리드 목록/CSV)
- 외부 연동(선택): 파일 상단 `CONFIG` — `submitEndpoint`(Formspree/Tally/Google Form)로 등록 데이터 전송, `paymentLink`(Stripe/Gumroad/Lemon Squeezy)로 **2단계 실제 결제** 연결. `window.gtag`(GA4)·`window.fbq`(Meta Pixel)가 있으면 이벤트 자동 전송.

> **정직한 신호 위계:** 좋아요·조회(관심) < 이메일 등록·"의향" 체크(*말*, 약함) < **예약금·사전결제(*돈*, 강함)**. 1단계 랜딩은 "관심"까지만 검증합니다 — **유료 니즈는 `paymentLink`로 실제 돈을 받는 2단계에서만 확인됩니다.** 스모크 테스트의 GO를 "수요 증명"으로 착각하지 마세요.

### 🧮 Tool 03 — `gate-calculator.html` · 단계별 합격선 계산기
측정값을 넣으면 단계마다 `GO`/`WATCH`/`KILL`을 판정.

- **합격선 잠금**: 테스트 *전에* 기준을 숫자로 박고 잠가서 사후 합리화 차단
- 1단계: CTA 클릭률·등록 전환율 + **표본 충분성 경고**(기본 100명 미만이면 신뢰 금지)
- 2단계: 실제 결제자 수, 등록→결제 전환율
- 3단계: 30일 리텐션 / 이탈률
- 4단계: **LTV·CAC·LTV:CAC 비율·CAC 회수기간** (3:1 룰)
- 종합 판정 + 다음 행동 제안

## 추천 사용 흐름

1. **Tool 01**에서 레딧 페인 10개를 점수화 → `GO` 상위 2~3개 선정
2. 선정된 문제마다 **Tool 02**로 랜딩을 만들어(문구만 교체) SNS·커뮤니티에 뿌림
3. **Tool 03**에서 *테스트 시작 전에* 합격선을 잠그고, 매일 수치를 입력해 `GO/KILL` 판정
4. 1단계를 통과한 것만 **선판매(실제 결제)**로 → 또 통과한 것만 **실제 개발** 시작

> 여러 개를 동시에 싸게 던지고, **지불 신호가 터진 1~2개에만 개발 자원을 몰빵**하는 게 이 방식의 진짜 강점입니다.

## 흔한 함정 (체크리스트)

- [ ] "반응"을 좋아요로 정의하지 않았는가? → **지불 신호(등록·클릭·사전결제)**로만 판정
- [ ] 합격선을 테스트 *전에* 숫자로 박았는가? (Tool 03 잠금)
- [ ] 표본이 충분한가? (100명 미만 전환율은 노이즈)
- [ ] 레딧 페인의 "지불 의향 증거"를 실제로 남겼는가?
- [ ] 무료엔 몰리는데 결제가 0이면 → 가격/패키징 문제로 인지했는가?
- [ ] 자동화는 *반복작업*에만, 유통·메시지·가격 *판단*은 사람이 하는가?

## 배포 방법 (택1)

- **로컬:** 파일을 브라우저로 그냥 열기 (`file://`)
- **GitHub Pages:** 저장소 Settings → Pages → 브랜치 지정 → `https://<id>.github.io/<repo>/`
- **Vercel / Netlify:** 저장소 연결 후 정적 사이트로 배포(빌드 명령 불필요)

## 데이터 & 프라이버시

모든 입력은 기본적으로 **브라우저 localStorage**에만 저장되며 서버로 전송되지 않습니다.
Tool 02의 `CONFIG.submitEndpoint`를 직접 설정한 경우에만 외부로 등록 데이터가 전송됩니다.

## 기술 메모

- 의존성·빌드 단계 없음. 바닐라 JS, 단일 파일 구조.
- 공용 스타일: `assets/app.css`
- 브라우저: 최신 Chrome/Safari/Firefox/Edge
