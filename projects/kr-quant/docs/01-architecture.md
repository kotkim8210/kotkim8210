# 1. 설계안 (Architecture)

## 1.1 시스템이 답해야 하는 질문

이 시스템은 "이 종목 오를까?"에 답하지 않는다. 다음 4개 질문에 답한다.

| 질문 | 담당 레이어 | 산출물 |
|---|---|---|
| Q1. 지금 이 종목은 **구조적으로 나빠지기를 멈췄는가?** | 재무·공시 피처 | F축·D축 점수 |
| Q2. **돈이 들어오고 있는가?** (가격보다 수급이 먼저 움직이는가) | 수급 피처 | S축 점수 |
| Q3. **장기 추세가 바뀌는 자리인가?** (주봉/월봉) | 기술 피처 | T축 점수 |
| Q4. **다수 의견이 틀렸다는 증거가 있는가?** | 텍스트·밸류에이션 | C축 점수 |
| Q5. **외부 촉매가 이 회사의 미래 재무제표를 바꾸는가?** | 시나리오 엔진 | E축 점수 |

Q1~Q4가 동시에 "예"일 때만 매수 후보가 된다. 그 외에는 전부 관망이다.
시스템의 가치는 *많이 찾는 것*이 아니라 *대부분을 걸러내는 것*에 있다.

Q5(시나리오)는 **가점이자 감점**이다. 정책·공시 촉매가 실제 실적으로 번역될 근거가 있으면 가점,
기대만 선반영되고 단타 수급이 이미 들어왔으면 감점 및 **신규 매수 거부권(veto)** 으로 작동한다.
시나리오 투자에서 가장 중요한 문장은 이것이다 — **"정책 그 자체가 아니라, 정책이 기업의 미래 재무제표를 바꾸는가."**

## 1.2 레이어 아키텍처

```
┌──────────────────────────────────────────────────────────────────────────┐
│ L6  REPORT      리포트 생성 (A~F 마크다운) + 기계용 JSON + 차트           │
│                 금칙어 필터("무조건 오른다"류) · 근거 각주 · 신뢰도 부여   │
├──────────────────────────────────────────────────────────────────────────┤
│ L5  BACKTEST    이벤트 드리븐 시뮬레이션 · PIT 접근자 · 비용/슬리피지     │
│                 워크포워드 · 민감도 · 다중검정 보정 · 패턴 마이닝          │
├──────────────────────────────────────────────────────────────────────────┤
│ L4  RULES       룰 엔진 (YAML DSL) · 하드/소프트 게이트 · 4중 동시충족    │
│                 매수/매도/경고 룰 · 과열 거부권 · 시나리오 상태머신        │
├──────────────────────────────────────────────────────────────────────────┤
│ L3b SCENARIO    ⭐촉매 엔진 — 정책/법령/예산/공시 이벤트 → 종목 매핑       │
│                 정책적합성 · 실적반영 · 선반영위험 · 단타과열 · 지속성     │
├──────────────────────────────────────────────────────────────────────────┤
│ L3a SCORING     7축 점수화 (재무·공시·수급·기술·시나리오·정성·역발상)     │
│                 업종 내 백분위 정규화 · 가중합 · 등급 · 기여도 분해        │
├──────────────────────────────────────────────────────────────────────────┤
│ L2  FEATURES    피처 계산 — fundamental / disclosure / flow / technical    │
│                 / text / event. 전부 `as_of(date)` 시그니처를 강제한다.    │
├──────────────────────────────────────────────────────────────────────────┤
│ L1  NORMALIZE   종목 마스터 · 계정과목 표준화 · 수정주가 · 분기 환산       │
│                 사업부문별 매출구성 · 재작성 이력 보존 · 단위 통일         │
├──────────────────────────────────────────────────────────────────────────┤
│ L0  COLLECT     DART · KRX · KIND · 네이버 검색API · 뉴스 · 커뮤니티       │
│                 + 정책브리핑 · 국가법령 · 열린국회 · 열린재정(예산)        │
│                 레이트리밋 · 재시도 · 증분 수집 · 원본 무손실 보존         │
└──────────────────────────────────────────────────────────────────────────┘
        ▲                                                          ▲
        │  횡단 관심사(cross-cutting)                               │
        └── config · cache · logging · errors · 감사추적(audit) ────┘
```

**단방향 의존 규칙:** 상위 레이어는 하위만 호출한다. L2가 L0을 직접 부르지 않는다(L1 경유).
이 규칙 하나가 "백테스트에서만 되고 실전에서 안 되는" 문제의 대부분을 막는다 —
실시간 경로와 백테스트 경로가 **L2 이상을 100% 공유**하기 때문이다.

## 1.3 핵심 불변식 (Invariants) — 위반 시 전체 결과 무효

### INV-1. PIT(Point-In-Time) 정합성 ★최우선

> 어떤 피처도 `as_of` 시점에 **실제로 공개되어 있던** 데이터만 사용한다.

한국 시장에서 이걸 어기는 전형적 실수:

| 실수 | 왜 치명적인가 |
|---|---|
| 2024년 사업보고서 수치를 2024-12-31 시점 피처에 사용 | 실제 공시는 2025-03-25경. **3개월 선견(lookahead)** |
| 재작성(restated)된 최신 재무제표를 과거 시점에 사용 | 당시엔 존재하지 않던 숫자. 턴어라운드 탐지가 인위적으로 쉬워짐 |
| 현재 상장된 종목만으로 유니버스 구성 | 상장폐지 종목 누락 = **생존편향**. 수익률이 구조적으로 부풀려짐 |
| 오늘 기준 수정주가로 과거 신호 판단 | 액면분할·무상증자 반영 시점 왜곡 |

**구현 강제 방식:** 모든 재무 레코드는 `(corp_code, fiscal_period, rcept_dt, report_type, value)` 형태로
**append-only** 저장한다. 조회는 반드시 다음 접근자만 통과한다.

```python
def get_financials(corp_code: str, as_of: date) -> FinancialFrame:
    """as_of 시점에 이미 접수된(rcept_dt <= as_of) 레코드 중,
    각 회계기간별로 가장 마지막에 접수된 버전만 반환한다."""
```

재작성 이력은 삭제하지 않고 보존한다 — `rcept_dt` 필터가 자동으로 "당시의 진실"을 복원한다.

### INV-2. 실시간 경로 = 백테스트 경로
`features/` 이상의 모든 코드는 백테스트와 실시간에서 **동일 함수**를 쓴다.
분기하는 곳은 L0/L1의 데이터 소스뿐이다.

### INV-3. 커뮤니티·기대 신호 상한
정성(Q 8점) + 역발상(C 7점) 가중치 합 ≤ 20/100. 두 축이 만점이어도 나머지 85점 중 55점 이상을
확보하지 못하면 매수 임계(70)를 넘을 수 없다. **"커뮤니티 여론만으로 매수하지 않는다"를 수식으로 강제한다.**

같은 원리를 시나리오 축에도 적용한다: E축 내부에서 **기대성 지표(E1 정책적합성)의 배점은
검증성 지표(E2 실적반영 가능성)보다 낮다.** 정책 테마에 이름만 엮인 종목이 고득점을 받는 경로를 차단한다.

### INV-4. 감사추적(Audit Trail)
모든 신호는 다음을 함께 저장한다: 입력 스냅샷 해시 · 룰 버전 · 설정 버전 · 축별 기여도 · 발동한 룰 ID.
"왜 이 종목이 나왔는가"를 사후에 100% 재현할 수 없으면 그 신호는 폐기한다.

### INV-5. 결측은 0이 아니다
데이터가 없는 것과 값이 나쁜 것은 다르다. 결측은 `None`으로 전파하고, 축 점수는
**관측된 하위지표만으로 재정규화**한다. 필수 지표 결측률이 40%를 넘으면 그 종목은 그 시점에서 평가 불가(`SKIP`)로 처리한다.

## 1.4 모듈 책임표

| 모듈 | 책임 | 하지 않는 일 |
|---|---|---|
| `collectors/` | 외부 API 호출, 원본 응답 무손실 저장, 레이트리밋 준수 | 파싱·해석·계산 |
| `normalize/` | 계정과목 매핑, 단위 통일, 수정주가, 종목 마스터 관리 | 투자 판단 |
| `features/` | `as_of` 기준 지표 계산. 순수함수. | I/O(주입받은 스토어만 사용) |
| `scenario/` | 촉매 이벤트 감지 → 종목 매핑 → 5개 시나리오 점수 → 상태머신 전이 | 최종 매수 결정(룰이 함) |
| `scoring/` | 피처 → 0~100 축 점수. 업종 내 백분위 정규화 | 매수/매도 결정 |
| `rules/` | 점수+피처 → 신호(BUY/HOLD/TRIM/EXIT). 게이트·거부권 판정 | 점수 계산 |
| `patterns/` | 패턴 매칭 및 과거 사례 마이닝 | 룰 실행 |
| `eventstudy/` | 공시·정책 유형별 초과수익(CAR) 곡선 산출 → 패턴/가중치 근거 제공 | 실시간 신호 생성 |
| `backtest/` | 시뮬레이션, 포트폴리오 회계, 성과 지표, 검증 | 피처/점수 재구현(L2~L4 재사용) |
| `report/` | MD/JSON 렌더링, 근거 각주, 금칙어 필터 | 계산 |

## 1.5 실행 모드

| 모드 | 트리거 | 대상 | 소요(목표) | 산출물 |
|---|---|---|---|---|
| `screen` | 일 1회(장 마감 후) | 전 종목 (~2,700) | < 10분 (캐시 히트 시) | 후보 랭킹 JSON + 요약 MD |
| `deepdive` | 사용자 요청 | 단일 종목 | < 60초 | A~F 리포트 MD + JSON |
| `watchlist` | 일 1회 | 보유·관심 종목 | < 1분 | 매도/경고 알림 |
| `scenario` | 일 1회 + 정책 발표 시 | 활성 시나리오 전체 | < 3분 | 시나리오 보드(단계별 종목 상태) |
| `backtest` | 수동 | 유니버스 × 기간 | 수십 분 | 성과 리포트 + 편향 체크리스트 |
| `eventstudy` | 주 1회 | 공시·정책 유형별 | 수십 분 | 유형별 CAR 곡선 (1주/1개월/3개월/6개월) |
| `mine` | 주 1회 | 과거 성공 사례 | 수십 분 | 패턴 후보 → `config/patterns.yaml` 제안 |

`screen`이 무거운 이유는 재무 때문이 아니라 **텍스트(뉴스·커뮤니티)** 때문이다.
따라서 텍스트 축(Q·C)은 **2단계 전략**을 쓴다:
1차로 F·D·S·T 4축만 계산해 상위 N개(기본 80종목)로 압축 → 그 종목에 대해서만 텍스트 수집.
전체 종목의 텍스트를 매일 긁는 설계는 비용·차단 양쪽에서 지속 불가능하다.

## 1.6 이벤트 컨텍스트 해석기 (Event Context Interpreter)

사용자 요구사항 §5의 핵심. **액면분할·무상증자·자사주 등은 고정된 부호를 갖지 않는다.**
같은 이벤트가 밸류에이션·수급 위치에 따라 정반대로 해석된다.

```
             ┌─────────────── 이벤트 발생(예: 액면분할 결정 공시) ───────────────┐
             │                                                                   │
        [직전 3년 수익률]      [밸류에이션 백분위]      [감성 백분위]      [수급 추세]
             │                       │                      │                 │
             └───────────────┬───────┴──────────────┬───────┴─────────────────┘
                             ▼                      ▼
                  ┌──────────────────┐   ┌──────────────────────┐
                  │ 저평가·저상승 구간 │   │ 고평가·급등 후 구간    │
                  │ = 접근성 개선     │   │ = 정점 신호 경계       │
                  │ (삼성전자 2018형) │   │ (카카오 2021형)        │
                  │ → 중립~약한 +     │   │ → 매도 경고 룰 활성화  │
                  └──────────────────┘   └──────────────────────┘
                             └──────────┬───────────┘
                                        ▼
                        분할 후 60일 수급(외인·기관 순매수)으로 **사후 검증**
                        → 판정을 확정하고 패턴 라이브러리에 라벨 축적
```

핵심은 **"분할 자체"가 아니라 "분할 이후의 사업·실적·수급·주가 위치"** 를 본다는 것이다.
상세 매트릭스와 조건문은 `docs/06-pattern-library.md` KP-10 참조.

## 1.7 시나리오 투자 파이프라인 ⭐

일반 가치·수급 투자와 **병렬로 돌아가는 두 번째 트랙**이다. 촉매(catalyst)에서 출발해
"기대 → 검증 → 재평가"의 시간 축을 따라간다. 핵심 방어선은 하나다:
**이벤트가 생겨도 즉시 매수하지 않는다. 후보군에 등록만 한다.**

### 1.7.1 촉매 분류

| 군 | 촉매 유형 | 주 소스 | 리드타임(주가 반영까지) |
|---|---|---|---|
| **정책군** | 정부 정책 발표, 산업 육성책 | 정책브리핑(korea.kr), 부처 보도자료 | 수개월~수년 |
| | 법·제도 변화, 규제 완화/강화 | 국가법령정보, 열린국회(의안) | 법안 발의→시행 6~24개월 |
| | 예산안·세제 개편 | 열린재정, 기재부 | 편성→집행 6~18개월 |
| **기업군** | 대규모 수주·공급계약 | DART 단일판매·공급계약체결 | 즉시~수분기(매출인식 시점) |
| | 증자·자사주·합병·구조조정 | DART 주요사항보고서 | 즉시~수개월 |
| | 최대주주 변경 | DART 최대주주변경 | 수개월~수년 |
| | 실적 서프라이즈·가이던스 변화 | DART 매출액/손익구조변동, IR | 즉시~2분기 |

### 1.7.2 4단계 추적 모델

```
 ①이벤트 발생        ②시장 기대 형성        ③실적/수급/차트 반응      ④중기 재평가
 ─────────────      ─────────────────      ──────────────────      ──────────────
 정책 발표          거래량·언급량 급증      실제 수주/매출 인식        멀티플 리레이팅
 공시 접수          테마 편입, 급등         외인·기관 순매수 전환      추세 정착 or 소멸
      │                    │                       │                      │
      ▼                    ▼                       ▼                      ▼
  [WATCH 등록]      ⚠️여기서 사지 않는다      ✅여기서 분할매수 개시     ✅여기서 비중확대
                    (선반영·과열 측정 구간)   (E2 실적반영 근거 확보)   (또는 기대소진 시 분할매도)
```

**②단계 매수 금지**가 이 트랙의 존재 이유다. 단타 추격매매와 시나리오 투자를 가르는 유일한 선이
"기대에 사느냐, 검증에 사느냐"이기 때문이다. 대신 ②단계에서는 **선반영 위험(E3)과 단타 과열(E4)을 측정**하여
③단계 진입 자격을 심사한다.

### 1.7.3 포지션 상태머신

각 (종목 × 시나리오) 쌍은 아래 상태를 갖는다. 상태는 `gold/scenario_positions.parquet`에 영속화된다.

```
        ┌───────────────────────────── 촉매 감지 ─────────────────────────────┐
        ▼                                                                     │
   ┌─────────┐  E1(정책적합)≥60      ┌──────────────┐   확인 3/4 충족   ┌──────────┐
   │  WATCH  │ ─── AND E2(실적반영)≥55 ─▶│ CONFIRM_     │ ───────────────▶│ SCALE_IN │
   │ (후보군) │                        │ PENDING      │   (실적·수급·   │ (분할매수)│
   └─────────┘                        │ (검증 대기)   │    차트·공시)    └────┬─────┘
        ▲                             └──────┬───────┘                        │
        │                                    │ 90일 내 미확인                  │ 실적·수급
        │                                    ▼        or 촉매 무효화           │ 후행 확인
        │                             ┌──────────────┐                        ▼
        └──── 재등록 ─────────────────│   LAPSED     │                  ┌──────────┐
                                      │  (기대 소진)  │◀────────────────│ SCALE_UP │
                                      └──────────────┘   기대 선소진     │ (비중확대)│
                                             │                          └────┬─────┘
                                             ▼                               │ 과열/기대소진
                                      ┌──────────────┐                       ▼
                                      │  EXIT/TRIM   │◀──────────────────────┘
                                      └──────────────┘
```

| 상태 | 진입 조건 | 허용 행동 |
|---|---|---|
| `WATCH` | 촉매 감지 + 종목 매핑 성공 | **매수 금지.** 모니터링만 |
| `CONFIRM_PENDING` | E1 ≥ 60 AND E2 ≥ 55 AND 과열거부권 미발동 | 매수 금지. 확인 지표 추적 |
| `SCALE_IN` | 확인 4항목(실적·수급·차트·공시) 중 **3개 이상** 충족 + 7축 종합 게이트 통과 | 1차 분할매수(계획의 40%) |
| `SCALE_UP` | 실적 또는 수급이 **후행 확인**(분기 실적 반영 or 외인·기관 60일 순매수 지속) | 2·3차 분할매수 |
| `LAPSED` | 90일 내 미확인 / 촉매 무효화 / 기대 선소진 | 신규 매수 중단, 보유분은 매도 룰로 이관 |
| `EXIT/TRIM` | 매도 룰 발동 | 분할매도 |

`WATCH`·`CONFIRM_PENDING`에서 **매수를 구조적으로 불가능하게 만든 것**이 §10-4 요구사항
("이벤트가 생기면 바로 매수하지 말고 우선 후보군에 등록")의 코드 수준 구현이다.

### 1.7.4 정책 → 종목 매핑 (§10-1의 핵심)

"관련주"라는 말이 가장 위험하다. 이 시스템은 연결 강도를 **매출 비중으로 정량화**한다.

```
정책 문서 ──▶ 키워드/산업 추출 ──▶ KSIC 업종코드 + 제품 키워드
                                          │
                                          ▼
                        기업 사업보고서 「사업의 내용」 + 부문별 매출 구성
                                          │
                                          ▼
              연결강도 = Σ(매칭 사업부문 매출비중) × 밸류체인 계수 × 정책 구체성 계수
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        ▼                                 ▼                                 ▼
   직접 수혜(1.0)                     1차 벤더(0.6)                    단순 연관(0.2)
   정책 대상 사업이                    수혜 기업에 납품                  업종만 같음
   매출의 30%+                        (수주 공시로 확인 가능)            → 대부분 여기서 탈락
```

이 계산이 §10-1의 질문들에 직접 답한다:
- *"업종 전체인지 개별 기업인지"* → 업종 내 연결강도 분산으로 판정(전원 고득점이면 업종 수혜)
- *"가장 먼저 실적이 개선될 기업"* → **수주 공시 리드타임 + 매출인식 주기**가 가장 짧은 기업
- *"이미 반영됐는지"* → E3 선반영 위험 점수
- *"과열 단타 수급이 들어왔는지"* → E4 단타 과열 점수 + 투자자별 매매동향(개인 순매수 집중도)

상세 산식은 `docs/03-scoring-rules.md` §3.7, 데이터 소스는 `docs/02-data-pipeline.md` §2.7 참조.

## 1.8 에러·품질 전략

| 상황 | 처리 |
|---|---|
| API 5xx / 타임아웃 | 지수 백오프 재시도(2s→4s→8s→16s, 최대 4회) → 실패 시 캐시 폴백 → 그래도 실패면 해당 피처 `None` |
| 레이트리밋 초과 | 토큰버킷으로 사전 차단. 일일 쿼터 80% 소진 시 경고, 95% 시 비필수 수집 중단 |
| 스키마 변경(필드 사라짐) | 파서가 `SchemaDriftError` 발생 → 원본은 저장, 파생만 실패. 알림 후 사람이 매핑 갱신 |
| 부분 결측 | INV-5에 따라 재정규화. 결측률 40% 초과 시 `SKIP` |
| 이상치(전기 대비 100배 등) | 단위 오류 의심 → 격리 큐에 넣고 자동 채택 금지 |
| 상장폐지/거래정지 | 유니버스에서 제외하되 **과거 데이터는 보존**(생존편향 방지) |

**Fail loud, not silent:** 데이터 문제로 점수가 낮게 나오는 것과 실제로 나쁜 것을 구분할 수 없게 만드는
"결측=0" 처리를 금지한다. 리포트에는 항상 `data_coverage` 필드를 함께 낸다.

## 1.9 저장소 전략 (3계층 레이크)

```
data/
├── bronze/   원본 무손실 (API 응답 원문, gzip JSON/XML). 절대 수정하지 않음.
├── silver/   정규화 테이블 (parquet, 파티션: /year=/month=)
│             financials · prices · flows · disclosures · master
│             segments(부문별 매출) · policies · bills(의안) · budgets
└── gold/     피처·점수·신호 (parquet + DuckDB 뷰)
              features · scores · signals · scenario_positions · event_car
```

- **Bronze는 진실의 원천.** 파싱 로직이 바뀌면 silver를 지우고 bronze에서 재생성한다.
- 조회는 DuckDB로 parquet에 직접 쿼리 — 별도 DB 서버 없이 수백만 행을 수 초에 처리한다.
- 개인 사용 규모(2,700종목 × 20년 일봉 ≈ 1,300만 행)에서 이 조합이 운영 부담 대비 최적이다.

## 1.10 설계상 알려진 한계 (정직한 고지)

1. **컨센서스(증권사 추정치) 확보가 어렵다.** 유료 데이터 없이는 "어닝 서프라이즈"를 정확히 계산할 수 없다.
   → 대체 프록시(전년동기 대비 + 자체 추세 외삽)를 쓰되, Q축 신뢰도를 낮추고 리포트에 명시한다. `[검증필요]`
2. **커뮤니티 데이터는 법적·기술적 제약이 크다.** robots.txt·이용약관·개인정보 이슈.
   → 공식 API(네이버 검색 API)와 공개 뉴스로 한정하는 것을 기본값으로 한다. `docs/02` §2.6 참조.
3. **소형주에서 수급 데이터의 신호대잡음비가 낮다.** 외국인·기관 순매수 절대금액이 작아 노이즈가 크다.
   → 유동성 게이트(시총·거래대금 하한)로 애초에 배제한다.
4. **정책·제도 변수는 코드가 아니라 설정으로 뺀다.** 증권거래세율, 공매도 제도, 배당기준일 제도 등은
   자주 바뀐다. 전부 `config/costs.yaml`·`config/settings.yaml`에 두고 `[확인필요]` 주석을 단다.
5. **패턴 라이브러리 초안의 사례 수치는 미검증이다.** `docs/06`의 대표 사례는 방향성 예시이며,
   실제 조건값은 `krq mine`으로 데이터에서 재도출해야 한다.
6. **정책 → 종목 매핑이 이 시스템에서 가장 노이즈가 큰 부분이다.** 정책 문서의 표현과 기업 사업보고서의
   표현이 어휘 수준에서 잘 맞지 않고("차세대 모빌리티" vs "자동차부품 제조"), 부문별 매출 공시의 세분화 정도가
   기업마다 다르다. 따라서 매핑 결과는 **자동 확정하지 않고 `WATCH` 상태로만 등록**하며,
   연결강도 상위 후보는 사람이 검토하는 경로를 남긴다. 매핑 정확도 자체를 `eventstudy`로 사후 채점한다. `[검증필요]`
7. **정책 시나리오는 표본이 적다.** 대형 정책 사이클은 수년에 한 번이라 통계적 유의성을 확보하기 어렵다.
   → E축 가중치를 15점으로 제한하고, 단독으로는 매수 결정을 만들 수 없게 설계했다.
