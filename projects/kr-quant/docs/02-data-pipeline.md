# 2. 데이터 파이프라인

## 2.0 이 문서의 신뢰도 표기

외부 API 사양은 자주 바뀐다. 각 항목에 검증 상태를 표기했다.

| 표기 | 의미 |
|---|---|
| ✅ | 엔드포인트·파라미터 구조를 신뢰 가능. 구현 시 바로 사용 |
| ⚠️ | 서비스는 실재하나 **정확한 엔드포인트명/필드명은 구현 전 공식 문서 확인 필요** |
| 🔶 | 비공식 경로(내부 JSON, HTML 파싱). 예고 없이 깨질 수 있음 → 어댑터로 격리 |

**구현 착수 시 첫 작업은 `tests/contract/` 의 계약 테스트 작성이다.** 각 소스마다 "1건 가져와서
필수 필드가 존재하는가"를 검사하는 테스트를 두고, CI에서 주기 실행해 스키마 드리프트를 조기에 잡는다.

## 2.1 소스 카탈로그 — 공시·재무 (DART)

**기본:** `https://opendart.fss.or.kr/api/{endpoint}` · 인증 파라미터 `crtfc_key` · 무료 발급
**쿼터:** 일 20,000건 수준 ⚠️(발급 페이지에서 재확인). 분당 버스트 제한도 존재하는 것으로 알려짐 → 토큰버킷 필수.

| 엔드포인트 | 용도 | 갱신 | 검증 |
|---|---|---|---|
| `corpCode.xml` | 고유번호(corp_code) ↔ 종목코드 전체 매핑 (ZIP) | 주 1회 | ✅ |
| `company.json` | 기업개황(업종, 결산월, 대표자, 설립일) | 월 1회 | ✅ |
| `list.json` | **공시검색** — 기간·기업·유형별 공시 목록. 파이프라인의 심장 | 일 1회 | ✅ |
| `fnlttSinglAcntAll.json` | 단일회사 **전체 재무제표** (연결/별도, 재무상태표·손익·현금흐름) | 분기 | ✅ |
| `fnlttSinglAcnt.json` | 단일회사 주요계정 (경량, 폴백용) | 분기 | ✅ |
| `fnlttMultiAcnt.json` | 다중회사 주요계정 (배치 수집 효율화) | 분기 | ✅ |
| `majorstock.json` | 대량보유상황보고 (5%룰) — 지분 변동 추적 | 일 1회 | ✅ |
| `elestock.json` | 임원·주요주주 특정증권등 소유상황 — **내부자 순매수 신호** | 일 1회 | ✅ |
| `hyslrChgSttus.json` | 최대주주 변동현황 | 분기 | ⚠️ |
| `tesstkAcqsDspsSttus.json` | 자기주식 취득·처분 현황 | 분기 | ⚠️ |
| `alotMatter.json` | 배당에 관한 사항 | 분기 | ⚠️ |
| `document.xml` | **공시서류 원본** (사업보고서 본문 XML/HTML) | 필요시 | ✅ |
| 주요사항보고서군 | 유·무상증자, CB/BW/EB 발행, 자사주 취득·처분 결정, 합병·분할, 영업양수도 | 일 1회 | ⚠️ |

> ⚠️ 주요사항보고서 계열은 결정 유형마다 개별 엔드포인트로 나뉘어 있다(예: 유상증자결정, 전환사채발행결정 …).
> 엔드포인트명은 DART 개발가이드에서 확인해 `collectors/dart/endpoints.py` 한 곳에 상수로 모은다.

### 2.1.1 재무 수집 전략 — PIT 저장이 전부다

```python
# 저장 스키마 (append-only, 절대 UPDATE 하지 않음)
financials(
    corp_code, stock_code,
    fiscal_year, fiscal_quarter,      # 회계기간
    report_type,                      # 사업/반기/분기 보고서
    consolidated,                     # True=연결(우선), False=별도
    rcept_no, rcept_dt,               # ★ 공시 접수번호/일자 = PIT 키
    account_id, account_nm, value,    # 표준화된 계정
    collected_at
)
```

`rcept_dt`가 없으면 그 레코드는 **백테스트에서 사용 불가**다. `list.json`으로 얻은 공시 메타에서
`rcept_dt`를 확보한 뒤 재무 API를 호출하고, 두 정보를 같이 적재한다.

**재작성(restatement) 처리:** 같은 `(corp_code, fiscal_year, fiscal_quarter)`에 대해 여러 `rcept_dt` 레코드가
공존하는 것이 정상이다. 지우지 않는다. 조회 시 `rcept_dt <= as_of` 필터 후 최신 1건을 선택하면
"그 시점의 진실"이 자동 복원된다.

**한국 시장 공시 캘린더** (12월 결산법인 기준, PIT 계산의 기준선):

| 보고서 | 대상 기간 | 법정 제출기한 | 실무상 데이터 가용 시점 |
|---|---|---|---|
| 사업보고서 | 전년 1~12월 | 사업연도 경과 후 90일 | 3월 하순 |
| 1분기보고서 | 1~3월 | 분기 경과 후 45일 | 5월 중순 |
| 반기보고서 | 1~6월 | 반기 경과 후 45일 | 8월 중순 |
| 3분기보고서 | 1~9월 | 분기 경과 후 45일 | 11월 중순 |

즉 **연간 재무의 "신선도"는 최악의 경우 15개월**이다. 이 지연을 메우는 것이 잠정실적 공시
(매출액 또는 손익구조 30% 이상 변동)와 수급·기술 축의 역할이다.

## 2.2 소스 카탈로그 — 시세·수급 (KRX)

| 소스 | 용도 | 검증 |
|---|---|---|
| `pykrx` (파이썬 패키지) | 일봉 OHLCV, 시가총액, 투자자별 순매수, PER/PBR/DIV | ✅ 권장 1차 경로 |
| `FinanceDataReader` | 종목 리스팅, 지수, **상장폐지 종목 목록** (생존편향 방지) | ⚠️ 상폐 리스팅 지원 범위 확인 |
| KRX 정보데이터시스템 내부 JSON | pykrx가 감싸는 원 경로 (`getJsonData.cmd` + `bld` 파라미터) | 🔶 어댑터로 격리 |
| KRX 공식 오픈API | 공식 인증키 기반 서비스 | ⚠️ 제공 범위·신청 절차 확인 |

**주요 pykrx 호출** (구현 시 어댑터 뒤에 숨긴다):

| 함수 | 획득 데이터 |
|---|---|
| `stock.get_market_ticker_list(date, market)` | 시점별 상장 종목 — **PIT 유니버스 구성에 필수** |
| `stock.get_market_ohlcv(fromdate, todate, ticker)` | 일봉 (수정주가 옵션 확인 필요) |
| `stock.get_market_cap(...)` | 시가총액, 상장주식수 |
| `stock.get_market_fundamental(...)` | PER·PBR·EPS·BPS·DIV·DPS |
| `stock.get_market_trading_value_by_date(...)` | 투자자별 거래대금 (개인/외국인/기관/연기금 등) |
| `stock.get_exhaustion_rates_of_foreign_investment(...)` | 외국인 보유율·한도소진율 |

### 2.2.1 수급 데이터의 함정

1. **투자자 분류가 시기별로 다르다.** "기관합계"의 하위 구성(금융투자·투신·연기금·사모 등)이 바뀐 이력이 있다.
   → 연기금을 분리 추적하되, 결측 구간에서는 기관합계로 폴백하고 `flow_granularity` 플래그를 남긴다.
2. **금액 vs 수량.** 순매수 "금액"을 기본으로 쓴다. 수량은 액면분할 시 불연속이 생긴다.
3. **소형주 노이즈.** 시총 하위 구간에서 외국인 순매수 절대금액은 신호가 되지 못한다.
   → 정규화: `순매수금액 / 시가총액` 및 `순매수금액 / 기간거래대금` 두 형태를 모두 계산.
4. **수정주가 일관성.** 가격은 수정주가, 거래대금은 명목 금액이다. 섞어 쓰면 회전율 계산이 틀어진다.

### 2.2.2 주봉·월봉 생성 규칙
일봉에서 리샘플한다(외부 주봉 데이터 신뢰하지 않음).
- 주봉: 월~금, **금요일 종가 기준**. 주 중간 휴장 무관하게 해당 주 마지막 거래일 종가.
- 월봉: 해당 월 마지막 거래일 종가.
- 거래정지 구간은 **가격을 전진 채움(ffill)하지 않는다.** `NaN`으로 두고 지표 계산에서 제외한다.
  (정지 구간을 ffill하면 변동성이 인위적으로 낮아져 기술 점수가 부풀려진다.)

## 2.3 소스 카탈로그 — KIND

`kind.krx.co.kr` — 공식 API 없음. HTML 파싱. 🔶

| 획득 항목 | 대체 가능성 |
|---|---|
| 관리종목·투자주의환기종목 지정 현황 | **하드 게이트에 필수.** 대체 어려움 |
| 시장경보(투자주의/경고/위험) 지정 | 단타 과열(E4) 판정에 유용 |
| 상장폐지 사유 발생·정리매매 | 생존편향 방지 + 하드 게이트 |
| 불성실공시법인 지정 | 신뢰도 감점 |

DART와 중복되는 정보는 DART를 우선한다. KIND는 **거래소 조치(제재·지정)** 정보 취득 목적으로만 쓴다.
파싱 실패 시 해당 게이트는 "판정 불가"로 두고 종목을 보수적으로 `SKIP` 처리한다 —
게이트를 통과시키는 방향으로 폴백하지 않는다.

## 2.4 소스 카탈로그 — 텍스트 (뉴스·커뮤니티)

### 2.4.1 기본 방침: 공식 API 우선, 스크래핑 최소화

커뮤니티 크롤링은 **이용약관·robots.txt·개인정보 문제**가 실재한다. 기본 구성은 공식 API로 한정한다.

| 소스 | 엔드포인트 | 용도 | 검증 |
|---|---|---|---|
| 네이버 검색 API | `openapi.naver.com/v1/search/news.json` | 뉴스 건수·헤드라인 | ✅ |
| | `/v1/search/blog.json`, `/v1/search/cafearticle.json` | 블로그·카페 **언급량**(본문 아님) | ✅ |
| **네이버 데이터랩** | `openapi.naver.com/v1/datalab/search` | ⭐**검색어 관심도 추이** | ✅ |
| RSS(언론사·정책브리핑) | 각 매체 RSS | 원문 링크 수집 | ✅ |

쿼터는 API별 일 25,000건 수준 ⚠️(개발자센터에서 확인). `screen`의 2단계 전략(상위 80종목만 텍스트 수집)이
이 쿼터 안에 들어가도록 설계된 것이다.

### 2.4.2 데이터랩이 핵심인 이유

§10-3(단타 회피)과 §11(단타 과열 점수)이 요구하는 "커뮤니티 과열"을 측정하는 데
**검색어 관심도 급증**이 가장 깨끗한 프록시다. 스크래핑 없이, 공식 API로, 시계열로 얻을 수 있다.

```
hype_z = (최근 7일 평균 관심도 − 과거 1년 평균) / 과거 1년 표준편차
```

`hype_z ≥ 3` 이면서 실적 확인이 없으면 §10-3의 첫 번째 경고 조건이 성립한다.

### 2.4.3 감성 분석

- 1차: 룰 기반 사전(금융 도메인 한국어 극성 사전) + 부정어 처리
- 2차: 소형 한국어 분류 모델 또는 LLM 배치 호출(상위 후보군에 한정)
- **핵심 요구(§2-4):** 감정적 선동 문구와 논리·근거를 분리한다.

```
evidence_ratio = (숫자·출처·공시번호를 포함한 문장 수) / (전체 문장 수)
```

`evidence_ratio`가 낮은 극단 감성은 **가중치를 낮춘다.** "무조건 오른다"·"집 팔아 사라" 류의
과열 관용구는 별도 사전(`config/overheat_lexicon.yaml`)으로 관리하며, 등장 빈도 자체를 E4 지표로 쓴다.

### 2.4.4 선택적 확장(사용자 판단 영역)
종목토론방 등 추가 소스는 **기본값에서 비활성**으로 둔다. 활성화하려면 `config/settings.yaml`의
`text.optional_sources`를 명시적으로 켜야 하며, 그 경우에도 robots.txt 준수·요청 간격·재배포 금지가
어댑터에 강제된다. 수집한 원문은 로컬에만 두고 리포트에는 **집계 통계만** 싣는다.

## 2.5 소스 카탈로그 — 정책·법령·예산 (시나리오 트랙) ⭐

§10-1의 정책 시나리오를 데이터로 다루기 위한 소스다. 전부 공공 오픈데이터라 법적 제약이 낮다.

| 소스 | 주소 | 획득 항목 | 갱신 | 검증 |
|---|---|---|---|---|
| 대한민국 정책브리핑 | `korea.kr` | 부처 보도자료·정책 발표 원문 (RSS 제공) | 일 1회 | ⚠️ RSS 경로 확인 |
| 국가법령정보 공동활용 | `open.law.go.kr` | 법령·시행령 제개정, 시행일자 | 일 1회 | ⚠️ 인증(OC) 방식 확인 |
| 열린국회정보 | `open.assembly.go.kr` | **의안(법률안) 발의·처리 현황** | 일 1회 | ⚠️ |
| 열린재정 | `openfiscaldata.go.kr` | 예산·기금 편성/집행 (사업별) | 분기 | ⚠️ |
| 공공데이터포털 | `data.go.kr` | 부처별 산업 통계·인허가 데이터 | 상이 | ✅ 포털 자체는 확실 |

### 2.5.1 정책 이벤트의 생애주기 = 매수 타이밍의 근거

```
법안 발의 ──▶ 상임위 통과 ──▶ 본회의 통과 ──▶ 공포 ──▶ 시행 ──▶ 예산 집행 ──▶ 발주/수주 ──▶ 매출 인식
   │             │              │            │        │          │            │            │
 기대 형성 ────────────────────────────────▶│        │          │            │◀─────────── 실적 확인
   (②단계: 매수 금지 구간)                    │        │          │            │   (③④단계: 매수 구간)
                                             └────────┴──────────┴────────────┘
                                              여기서부터 "실적 반영 가능성(E2)"이 측정 가능해진다
```

이 타임라인이 시나리오 트랙의 **시간 축 근거**다. 발의 단계의 기대만으로는 E2를 올릴 수 없고,
**예산 집행·발주·수주 공시**가 나와야 E2가 상승한다. 그래서 정책 소스와 DART 수주 공시를
같은 시나리오 ID로 묶어 추적한다.

### 2.5.2 시나리오 카탈로그 스키마

```python
scenarios(
    scenario_id, title, catalyst_type,   # policy | regulation | budget | corporate
    source_url, announced_at,            # ★ PIT 키
    lifecycle_stage,                     # proposed|passed|promulgated|effective|budgeted|contracted
    keywords[], ksic_codes[],            # 산업 매핑용
    expected_lead_months,                # 실적 반영까지 예상 리드타임
    status,                              # active | lapsed | realized
    evidence_urls[]
)
scenario_links(
    scenario_id, stock_code,
    link_strength,                       # 0~1 (매출비중 × 밸류체인계수 × 구체성계수)
    link_basis,                          # 근거 텍스트 (감사추적)
    verified_by                          # auto | human
)
```

### 2.5.3 정책 → 종목 매핑에 필요한 기업 측 데이터

연결강도 계산의 분모가 되는 **부문별 매출 구성**은 DART 정형 API로 깔끔하게 나오지 않는다.
사업보고서 본문(`document.xml`)의 「사업의 내용」 섹션을 파싱해야 한다.

- 난이도: 높음. 기업마다 표 구조·용어가 다르다.
- 전략: (1) 표 추출 → (2) LLM으로 `{부문명, 제품, 매출액, 비중}` 정규화 → (3) 사람 검토 큐
- 갱신 주기: 연 1회(사업보고서)면 충분 — 사업 구성은 자주 바뀌지 않는다.
- **폴백:** 파싱 실패 시 KSIC 업종코드만으로 매핑하되 `link_strength`에 0.5 페널티를 곱하고
  `verified_by='auto_low'`로 표시한다. 이 종목은 `WATCH`에서 자동 승격되지 않는다.

## 2.7 레이트리밋 · 캐시 · 재시도

### 2.7.1 3중 방어

```
요청 ──▶ [L1: 메모리 LRU]  ──miss──▶ [L2: 디스크 캐시]  ──miss──▶ [토큰버킷] ──▶ 외부 API
          (동일 세션 중복)            (TTL + 콘텐츠 해시)         (쿼터 강제)
```

| 데이터 종류 | 캐시 TTL | 근거 |
|---|---|---|
| `corpCode`, 기업개황 | 30일 | 거의 안 변함 |
| 과거 일봉(D-2 이전) | 무기한 | **불변 데이터** — 재수집 금지 |
| 당일 일봉·수급 | 당일 18시까지 1시간, 이후 무기한 | 장중 정정 가능성 |
| 재무제표 | 무기한 (rcept_no 단위) | 접수번호가 다르면 다른 레코드 |
| 공시 목록 | 6시간 | 증분 수집 |
| 뉴스·데이터랩 | 24시간 | 쿼터 절약 |
| 정책·법령 | 7일 | 갱신 빈도 낮음 |

**"과거 일봉은 불변"** 이 캐시 전략의 핵심이다. 20년치를 한 번만 받으면 이후 매일 받는 것은 1일치뿐이다.
초기 적재(`make bootstrap`)만 오래 걸리고 일상 운영은 가볍다.

### 2.7.2 쿼터 관리

```yaml
# config/settings.yaml 발췌
rate_limits:
  dart:  { daily: 20000, per_second: 5,  reserve_pct: 20 }   # reserve: 긴급 조회용 확보
  naver: { daily: 25000, per_second: 10, reserve_pct: 10 }
  krx:   { per_second: 2 }                                   # 비공식 경로 → 보수적으로
```

- 일일 쿼터 **80% 소진 시** 경고 로그 + 비필수 작업(텍스트 수집) 후순위로 전환
- **95% 소진 시** 필수 작업(재무·시세)만 남기고 중단
- 남은 쿼터는 `deepdive` 요청용으로 `reserve_pct` 만큼 항상 확보

### 2.7.3 재시도 정책

| 응답 | 처리 |
|---|---|
| 429 / 5xx / 타임아웃 | 지수 백오프 재시도 (2s→4s→8s→16s, 최대 4회) + 지터 |
| 4xx (429 제외) | 재시도 금지. 요청 오류이므로 로그 남기고 실패 처리 |
| 빈 응답 / 데이터 없음 | 정상 케이스로 취급 (신규 상장사 등). `None` 반환, 오류 아님 |
| 스키마 불일치 | `SchemaDriftError` — bronze에는 저장, silver 변환만 실패. 알림 발송 |

## 2.8 결측 · 이상치 처리

| 상황 | 규칙 |
|---|---|
| 재무 항목 결측 | `None` 전파. **0으로 대체 금지**(INV-5) |
| 축 하위지표 일부 결측 | 관측된 지표만으로 배점 재정규화. `coverage` 기록 |
| 필수 지표 결측률 > 40% | 종목을 해당 시점 `SKIP`. 점수 산출하지 않음 |
| 상장 3년 미만 | 재무 추세 판단 불가 → 소프트 게이트 감점 + `data_coverage` 명시 |
| 전기 대비 100배 이상 변동 | 단위 오류 의심 → 격리 큐. 자동 채택 금지 |
| 결산월 변경 | 회계기간 재정렬. 변경 분기는 지표 계산에서 제외 |
| 액면분할·병합 | 수정주가 계수 적용. 상장주식수 시계열 불연속 지점 기록 |
| 거래정지 | 가격 `NaN` 유지(ffill 금지). 정지 해제 후 N일간 기술 지표 유예 |

**단위 통일:** 재무는 전부 **원(KRW) 단위 정수**로 저장한다. DART 응답의 천원/백만원 표기를 파서에서 흡수한다.
비율 지표는 소수(0.15)로 저장하고 표시 시점에만 %로 변환한다.

## 2.9 데이터 품질(DQ) 체크

매 수집 후 자동 실행. 실패 시 해당 배치를 gold로 승격하지 않는다.

| ID | 검사 | 실패 시 |
|---|---|---|
| DQ-01 | 모든 재무 레코드에 `rcept_dt`가 존재하는가 | **차단** (PIT 불가) |
| DQ-02 | 자산 = 부채 + 자본 (허용오차 0.1%) | 경고 + 격리 |
| DQ-03 | 일봉에 `고가 ≥ 종가 ≥ 저가` 성립 | 차단 |
| DQ-04 | 일간 등락률이 ±31% 범위 내 (가격제한폭) | 경고 — 액면분할 미반영 의심 |
| DQ-05 | 거래일 수가 시장 캘린더와 일치 | 경고 |
| DQ-06 | 투자자별 순매수 합계 ≈ 0 (매수=매도) | 경고 |
| DQ-07 | 유니버스에 상장폐지 종목이 과거 시점에 존재하는가 | **차단** (생존편향) |
| DQ-08 | 동일 `(corp, 기간)` 재무의 최신 버전이 유일한가 | 경고 |
| DQ-09 | 시나리오 링크의 `link_basis`가 비어있지 않은가 | 차단 (감사추적) |

## 2.10 PIT 접근자 — 전 시스템의 단일 관문

모든 L2 이상 코드는 이 인터페이스만 통과한다. 직접 parquet를 읽는 코드는 리뷰에서 반려한다.

```python
class PITStore:
    """as_of 시점에 공개되어 있던 데이터만 반환하는 읽기 전용 뷰."""

    def universe(self, as_of: date) -> list[str]:
        """그 시점 상장 종목. 이후 상장폐지된 종목도 포함한다."""

    def prices(self, code: str, as_of: date, lookback: int) -> pd.DataFrame: ...

    def financials(self, code: str, as_of: date, periods: int = 20) -> pd.DataFrame:
        """rcept_dt <= as_of 필터 후 회계기간별 최신 1건."""

    def flows(self, code: str, as_of: date, lookback: int) -> pd.DataFrame: ...

    def disclosures(self, code: str, as_of: date, lookback: int) -> pd.DataFrame: ...

    def scenarios(self, as_of: date, stock: str | None = None) -> pd.DataFrame:
        """announced_at <= as_of 인 시나리오와 링크."""

    def text_stats(self, code: str, as_of: date, lookback: int) -> pd.DataFrame:
        """언급량·감성·검색관심도 집계. 원문은 반환하지 않는다."""
```

`as_of=date.today()`를 넣으면 실시간 모드, 과거 날짜를 넣으면 백테스트 모드다.
**두 모드의 코드 경로가 완전히 동일하다**(INV-2). 이 설계 하나가 "백테스트에서만 되는 전략"을 원천 차단한다.
