# 4. 백테스트 구조

## 4.1 백테스트가 답해야 하는 질문

"수익률이 얼마였나"는 **네 번째로 중요한 질문**이다. 순서대로:

1. **이 결과는 편향의 산물인가?** (선견·생존·재작성 편향 제거 검증)
2. **표본 외(OOS)에서도 작동하는가?** (워크포워드)
3. **파라미터를 조금 바꿔도 유지되는가?** (민감도 — 절벽이면 과최적화)
4. 수익률·MDD는 얼마인가?

1~3을 통과하지 못한 4번은 의미가 없다. 엔진은 이 순서를 강제하도록 설계한다 —
`krq backtest`는 편향 체크리스트를 먼저 출력하고, 하나라도 실패하면 **성과 수치를 표시하지 않는다.**

## 4.2 이벤트 드리븐 엔진

### 4.2.1 루프 구조

```python
for d in trading_days(start, end):
    store = PITStore(as_of=d)            # ★ 이 시점 이후 데이터는 물리적으로 접근 불가

    portfolio.mark_to_market(store.prices_today())
    fills = broker.execute(pending_orders, store)   # 전일 신호 → 당일 시가 체결
    portfolio.apply(fills)

    if is_rebalance_day(d):                          # 기본: 매주 금요일
        universe = store.universe(d)                 # 상장폐지 종목 포함
        feats    = compute_features(universe, store) # L2 — 실시간과 동일 코드
        scores   = score(feats, store)               # L3
        signals  = rules.evaluate(scores, feats, portfolio)  # L4
        pending_orders = portfolio.plan(signals)     # 사이징·제약 적용

    ledger.append(d, portfolio.snapshot(), signals_hash, config_hash)
```

**핵심은 `PITStore(as_of=d)`가 유일한 데이터 통로라는 것.** 미래 데이터를 실수로 참조할 경로 자체가 없다.
전역 DataFrame을 직접 읽는 코드가 하나라도 있으면 이 보장이 무너지므로, 린터 규칙으로 금지한다.

### 4.2.2 시간 규약 (오프바이원 방지)

| 시점 | 사용 가능한 정보 |
|---|---|
| D일 장 마감 후 | D일 종가·거래량·수급, D일까지 접수된 공시 |
| D+1 시가 | **체결 시점** |

신호일 종가로 체결하는 백테스트는 전부 낙관 편향이다. **D일 신호 → D+1 시가 체결**을 고정 규약으로 한다.

### 4.2.3 리밸런싱

| 항목 | 기본값 |
|---|---|
| 주기 | 주 1회 (금요일 종가 기준 → 다음 거래일 시가 체결) |
| 신규 편입 | 게이트 통과 + TOTAL 랭킹 상위 |
| 기존 보유 | 매도 룰 우선 평가 → 미발동 시 유지 (**랭킹에서 밀렸다고 팔지 않는다**) |
| 분할매수 진행 | 매 리밸런스일에 2·3차 조건 점검 |

중장기 전략이므로 **회전율을 낮게 유지**하는 것이 설계 목표다. 보유 종목을 순위 변동만으로
교체하면 비용이 수익을 잠식하고 사실상 단타가 된다.

## 4.3 유니버스 — 생존편향 제거

```python
def universe(as_of: date) -> list[str]:
    """as_of 시점에 '실제로 거래 가능했던' 종목 전체.
    오늘 상장폐지된 종목도 당시에는 포함되어야 한다."""
    listed = master[(master.listing_date <= as_of) &
                    ((master.delisting_date.isna()) | (master.delisting_date > as_of))]
    return listed.code.tolist()
```

| 필수 처리 | 이유 |
|---|---|
| 상장폐지 종목의 과거 데이터 보존 | 없으면 수익률이 구조적으로 부풀려진다 |
| 상장폐지 시 **정리매매 종가로 청산** 처리 | 0원 처리는 과도, 무시는 낙관 편향 |
| 거래정지 구간 체결 불가 | 정지 중 매도 가능으로 가정하면 MDD가 과소평가된다 |
| 시점별 시장구분(코스피/코스닥/코넥스) 변경 이력 | 이전 상장 종목 처리 |

> DQ-07 검사가 이걸 감시한다: 과거 시점 유니버스에 현재 상장폐지 종목이 **하나도 없으면**
> 데이터 구성이 잘못된 것이다(차단).

## 4.4 체결 · 비용 · 슬리피지

### 4.4.1 체결 가능성 (한국 시장 특수 규칙)

| 상황 | 처리 |
|---|---|
| D+1 시가가 상한가(+29% 이상) | **체결 불가** — 다음 날로 이월, 3일 미체결 시 주문 취소 |
| D+1 하한가 근처 매도 | 체결 불가 처리 |
| 거래정지 | 체결 불가 |
| 주문금액 > 당일 거래대금 × 1% | 초과분 미체결 (분할 체결) |

상한가 체결 가정은 백테스트를 극적으로 왜곡한다. 급등 신호 전략일수록 이 처리 유무로 결과가 뒤집힌다.

### 4.4.2 비용 모델

```yaml
# config/costs.yaml — 세율·수수료는 제도 변경이 잦으므로 전부 외부화 [확인필요]
commission:
  buy_bps: 1.5          # 0.015%
  sell_bps: 1.5
tax:
  sell_kospi_bps: 15    # 증권거래세+농특세 합산 [확인필요 — 시행 시점별 세율 상이]
  sell_kosdaq_bps: 15   # [확인필요]
slippage:
  base_bps: 10                  # 최소 0.10%
  impact_coef: 0.3              # 시장충격 계수
  # 실효 슬리피지 = max(base_bps, impact_coef × (주문금액/당일거래대금) × 10000) bps
```

> ⚠️ 증권거래세율은 여러 차례 개정되었다. **백테스트 기간별로 당시 세율을 적용**해야 하며,
> `costs.yaml`에 `effective_from` 필드를 둔 시계열 테이블로 관리한다. 단일 고정값 사용은 오차 원인이다.

### 4.4.3 슬리피지가 전략을 죽이는 지점
소형주에서 목표 비중 6%를 채우려면 며칠에 걸쳐 사야 한다. 이 현실을 반영하지 않으면
"소형주 알파"가 대부분 환상으로 드러난다. G6(유동성 하드게이트)이 있는 이유가 이것이다.
백테스트는 **유동성 제약 유무 두 가지 버전을 모두 출력**하고 그 격차를 리포트에 명시한다.

## 4.5 성과 지표

| 범주 | 지표 |
|---|---|
| 수익 | 누적수익률, **CAGR**, 연도별 수익률 |
| 위험 | **MDD**, 최대 손실 지속기간, 연변동성, 하방편차 |
| 위험조정 | **Sharpe**, Sortino, **Calmar**(CAGR/MDD) |
| 거래 | 승률, 손익비, Profit Factor, 평균 보유기간, **연간 회전율** |
| 벤치마크 대비 | 초과수익, **정보비율(IR)**, 베타, 젠센 알파, 상승/하락장 포착률 |
| 안정성 | **롤링 3년 CAGR·Sharpe**, 연속 손실 최대 개월수 |
| 귀속 | **축별 기여도 분해**(F·D·S·T·E·Q·C), 트랙별(일반/시나리오) |

벤치마크: KOSPI, KOSDAQ, 코스피200, **동일가중 전체시장**(가장 정직한 비교 기준).

### 반드시 함께 보는 조합
- **CAGR 단독은 의미 없다** → Calmar(수익/최대낙폭)와 롤링 3년 성과를 같이 본다.
- **승률 단독은 의미 없다** → 손익비와 같이 본다. 승률 70%·손익비 0.3은 파산 경로다.
- **전체 기간 Sharpe 단독은 위험하다** → 특정 2년이 전체를 만든 것인지 롤링으로 확인한다.

## 4.6 편향 체크리스트 (자동 검사)

`krq backtest`는 아래를 **먼저** 실행하고, 실패 항목이 있으면 성과 수치를 출력하지 않는다.

| ID | 검사 | 방법 |
|---|---|---|
| B-01 | 선견 편향 (재무) | 모든 사용 재무 레코드의 `rcept_dt <= as_of` 단언 |
| B-02 | 선견 편향 (가격) | 피처 계산 시 `as_of` 이후 봉 참조 금지 (스토어 레벨 차단 + 감사로그) |
| B-03 | 생존 편향 | 과거 유니버스에 상장폐지 종목 포함 여부 + 비율 리포트 |
| B-04 | 재작성 편향 | 동일 회계기간 다중 버전 존재 시 최신본 사용 여부 검사 |
| B-05 | 체결 편향 | 상한가·거래정지 체결 건수 = 0 확인 |
| B-06 | 비용 누락 | 총비용/총거래대금 비율이 기대 범위 내인지 |
| B-07 | 데이터 스누핑 | 시도 횟수 레지스트리 존재 여부 (§4.8) |
| B-08 | 유동성 비현실 | 단일 주문이 당일 거래대금 1% 초과한 건수 = 0 |

## 4.7 이벤트 스터디 엔진 (§10-2 구현) ⭐

> "공시 기반 상승은 '즉시 급등'보다 '지연된 중기 상승'이 더 중요할 수 있으므로,
> 공시 후 1주·1개월·3개월·6개월 누적 성과를 반드시 추적한다."

이 요구를 **초과수익(CAR, Cumulative Abnormal Return)** 프레임으로 정식화한다.
단순 수익률이 아니라 **시장·업종을 제거한 초과분**을 봐야 "그 공시가 만든 효과"를 분리할 수 있다.

### 4.7.1 계산

```
추정 윈도우: [t−250, t−30]  →  시장모형 회귀로 α, β 추정
                                 r_i = α + β·r_mkt + ε

이벤트 윈도우: t = 0(공시일 다음 거래일 시가 기준)
  AR_t  = r_i,t − (α + β·r_mkt,t)          # 초과수익
  CAR   = Σ AR_t

측정 구간(거래일 기준):
  1주 = [0, +5]  │  1개월 = [0, +21]  │  3개월 = [0, +63]  │  6개월 = [0, +126]
```

- 벤치마크는 시장지수와 **업종지수 두 버전**을 모두 산출한다(업종 전체가 오른 것인지 구분).
- 유의성은 **부트스트랩 신뢰구간**으로 판정한다(수익률 정규성 가정 불필요).
- 표본 수 < 30인 이벤트 유형은 결과를 참고용으로만 표시하고 룰에 반영하지 않는다.

### 4.7.2 이 엔진이 답하는 것 — §10-2의 질문들

| §10-2 질문 | 이벤트 스터디에서의 답 |
|---|---|
| 호재 공시가 실적 개선으로 이어지는가 | 공시 후 4개 분기 매출·영업이익 YoY 변화를 CAR과 교차 집계 |
| 단기 기대감만 있는가 | CAR(1주) 큼 + CAR(6개월) ≈ 0 → **"즉시급등·소멸형"** |
| 공시 직후 급등 후 장기 유지되는가 | CAR 곡선 형태 분류 (아래) |
| 공시 이후 수급이 붙는가 | **조건부 분할**: 외인·기관 20일 순매수 (+)/(−) 그룹의 CAR 비교 |
| 실적이 따라오는가, 테마만 소멸하는가 | 실적 확인 그룹 vs 미확인 그룹의 CAR(6개월) 격차 |

### 4.7.3 CAR 곡선 유형 분류

```
   CAR                                     이 분류가 룰 가중치의 근거가 된다
    │
    │      ╭──╮                  A. 즉시급등·소멸형 (spike & fade)
    │     ╱    ╲___________         → 추격매수 금지 유형. E3 선반영 가중 ↑
    │    ╱
    ├───╯─────────────────────
    │
    │            ╭───────────    B. 지연상승형 (delayed drift)  ★가장 가치 있음
    │        ╭──╯                   → 공시 후 수주~수개월에 걸쳐 초과수익 누적
    │    ╭──╯                       → 시나리오 트랙이 노리는 구간
    ├───╯─────────────────────
    │
    │   ╲                        C. 지속하락형
    │    ╲______________            → 악재 또는 희석성 공시
    └────────────────────────▶ 거래일
      0    5   21    63    126
```

**조건부 분할이 핵심이다.** 같은 공시 유형이라도 "외인·기관 순매수가 붙은 그룹"만 B형이 되고
나머지는 A형인 경우가 흔하다. 그 격차가 바로 §10-2가 요구한 "수급이 붙는가"의 정량적 근거이며,
이 결과로 §3.7.5의 **확인 4항목 중 '수급 확인'의 임계값을 데이터에서 결정**한다.

### 4.7.4 정책 이벤트에도 동일 적용
정책 발표일을 t=0으로 두고 `link_strength` 구간별(직접수혜/1차벤더/단순연관) CAR을 비교한다.
"단순 연관 종목의 CAR(6개월)이 0에 수렴"하는 것이 확인되면, 그것이 밸류체인 계수 0.2의 실증 근거가 된다.

## 4.8 검증 프로토콜 — 과최적화와의 싸움

### 4.8.1 워크포워드

```
[학습 3년][검증 1년]
      [학습 3년][검증 1년]
            [학습 3년][검증 1년]  ...  1년씩 전진

· 학습 구간: 가중치·임계값 튜닝 허용
· 검증 구간: 조회만. 튜닝 금지
· 최종 성과 = 검증 구간들을 이어붙인 것 (학습 구간 성과는 보고하지 않음)
```

### 4.8.2 퍼지드 K-폴드 + 엠바고
보유기간이 수개월인 전략은 라벨이 겹쳐(overlapping) 일반 K-폴드가 정보를 누수시킨다.
- **Purging:** 검증 구간과 시간적으로 겹치는 학습 표본 제거
- **Embargo:** 검증 구간 직후 일정 기간(보유기간 만큼)을 학습에서 배제

### 4.8.3 파라미터 민감도 — 절벽이면 버린다

```
   성과                          성과
    │   ╭─────────╮               │        ╱╲
    │  ╱           ╲              │       ╱  ╲
    │ ╱             ╲             │      ╱    ╲
    └────────────────▶ 파라미터    └────────────▶ 파라미터
    ✅ 고원(plateau) = 견고        ❌ 첨봉(spike) = 과최적화
```

각 임계값을 ±20% 흔들어도 성과 순위가 유지되어야 채택한다.
**최적점이 아니라 고원의 중앙값을 최종 파라미터로 쓴다.**

### 4.8.4 다중검정 보정
여러 조합을 시도하면 우연히 좋아 보이는 것이 반드시 나온다. 그래서:

- **시도 레지스트리:** 모든 백테스트 실행을 `data/gold/trials.parquet`에 자동 기록
  (설정 해시, 성과, 실행 시각). 시도 횟수 N을 속일 수 없게 만든다.
- **Deflated Sharpe Ratio:** 시도 횟수 N과 수익률 왜도·첨도를 반영해 Sharpe를 할인한다.
  DSR이 유의하지 않으면 채택하지 않는다.
- **랜덤 대조군:** 같은 제약(종목 수·업종 한도·회전율) 하에서 무작위 포트폴리오 1,000회를 돌려
  전략 성과의 백분위를 구한다. **상위 5% 밖이면 알파 주장 불가.**

### 4.8.5 사전 등록 규칙 (Pre-registration)
룰을 추가·수정할 때는 **백테스트를 돌리기 전에** 근거와 예상 효과를 `docs/changelog-rules.md`에 적는다.
결과를 보고 나서 사후에 이유를 만드는 것(HARKing)을 막는 장치다. 번거롭지만, 이 규칙 하나가
"과거에만 잘 맞는 시스템"을 만들 확률을 크게 낮춘다.

### 4.8.6 시나리오 트랙의 별도 검증
정책 시나리오는 **표본이 근본적으로 적다**(대형 정책 사이클은 수년에 한 번).
- 일반 트랙과 **분리해서** 성과를 보고한다. 합산하면 표본 부족이 가려진다.
- 부트스트랩 신뢰구간을 반드시 병기하고, 신뢰구간이 0을 포함하면 "유의한 알파 없음"으로 명시한다.
- 표본 < 30이면 **가중치를 올리지 않는다.** E축 15점 상한을 유지하는 근거다.

## 4.9 패턴 마이닝 파이프라인 (`krq mine`)

과거 성공 사례에서 조건을 **역으로 추출**해 패턴 라이브러리를 갱신한다.

```
① 라벨링      성공 = 진입 후 12개월 초과수익 ≥ +30% AND 최대낙폭 ≥ −25% 아님
              실패 = 12개월 초과수익 ≤ −10%
              (임계값은 config/patterns.yaml)
      ▼
② 특징 추출   라벨 시점의 전체 피처 벡터 스냅샷 (PIT 준수)
      ▼
③ 조건 마이닝 성공군 vs 실패군에서 판별력 있는 조건 조합 탐색
              · 결정트리(깊이 ≤ 3) → 사람이 읽을 수 있는 규칙만 채택
              · 최소 지지도(support) 30건 이상
      ▼
④ 검증        OOS 구간에서 해당 조건의 성과 확인 + 랜덤 대조군 비교
      ▼
⑤ 제안        config/patterns.yaml 에 후보로 기록 (status: proposed)
              ★자동 반영하지 않는다. 사람이 승인해야 active 로 전환
```

**깊이 3 제한**은 성능이 아니라 해석 가능성을 위한 것이다. 설명할 수 없는 규칙은
왜 실패하는지도 알 수 없으므로 운용할 수 없다.

`status: proposed → active` 전환은 사람의 승인을 요구한다. 이것이 시스템이
스스로를 과최적화하는 폭주 경로를 막는 마지막 안전장치다.

## 4.10 백테스트 리포트 구성

```
1. 편향 체크리스트          ← 실패 시 여기서 중단, 이하 미출력
2. 검증 프로토콜 결과       워크포워드 OOS 성과 / DSR / 랜덤 대조군 백분위
3. 성과 요약                CAGR·MDD·Sharpe·Calmar·IR (벤치마크 4종 대비)
4. 안정성                   롤링 3년, 연도별, 상승장/하락장 분리
5. 거래 통계                승률·손익비·회전율·평균보유기간·비용 총액
6. 귀속 분석                축별 기여도, 트랙별(일반/시나리오), 업종별
7. 민감도                   주요 파라미터 ±20% 히트맵
8. 실패 사례 분석           손실 상위 10건의 축 점수 + 발동 룰 (★가장 유용한 섹션)
9. 한계 및 미검증 항목      데이터 커버리지, 프록시 사용 비율, 표본 부족 구간
```

**8번을 매번 읽는 것이 이 시스템을 개선하는 가장 빠른 길이다.**
"어떤 종목이 왜 통과했고 왜 틀렸는가"가 다음 룰 개선의 유일한 근거다.
