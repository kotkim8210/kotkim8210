## 2. 근본 원인 — 헤더/내용 불일치 (한진 자체 양식)

업로드 파일은 **해달 양식이 아니라 한진 양식**이다. 헤더와 실제 값이 어긋나 있다.

| 열 | 파일에 적힌 헤더 | 실제 담긴 값 | 판정 |
|---|---|---|---|
| P | `지불조건` | `463207503463`, `...474`, `...485`, `...496` (12자리) | ❗ **운송장번호가 "지불조건" 헤더 밑에 있음** |
| Q | `출고번호` | `한진` | ❗ **택배사명이 "출고번호" 헤더 밑에 있음** |

정량 근거:
- 헤더 22개 중 `운송장`/`송장`/`tracking`/`invoice` 포함 = **0개**
- 12자리 숫자 패턴이 실제로 존재하는 열 = **P열 단 하나** (4건 전부)
- 숨김 행/열 0, 병합셀 0, 시트 1개 → 다른 곳에 숨어있을 가능성 없음

→ 헤더명으로 운송장 컬럼을 찾는 파서는 **반드시** 실패한다.

### 쿠팡·토스가 동일 문구로 실패한 것이 결정적 증거
두 버튼은 서로 다른 엔드포인트를 호출하는데 에러 문구가 완전히 동일하다.
→ 플랫폼별 로직 진입 **이전의 공용 "해달 발주서 리더"** 단계에서 터진다는 뜻.
→ 쿠팡 API 연동 문제도, 토스 인증 문제도 아니다. **파일 파싱 문제 하나뿐.**

## 3. 아직 안 터진 두 번째 지뢰 — 주문 매칭 키 부재

P열을 읽게 만들어도 다음 단계에서 막힐 수 있다.

- 파일 전체에 `주문번호`/`묶음배송번호`/`상품주문번호`/`orderId` 컬럼 = **0개**
- 메모2·3·4 (T·U·V열) = **전부 비어 있음** ← 발주서 생성 시 주문번호를 심어 왕복시킬 자리인데 비었음
- 매칭에 쓸 수 있는 건 A(수취인명) + B(안심번호)뿐
- 안심번호 접두사가 섞여 있음: `0502-`(3건) / `0504-`(1건) → 플랫폼/발급사 상이 가능성
- 동명이인 위험: 같은 코드베이스의 `gaegeolmu-tracking`이 "동명이인 자동 감지"를 광고 → **개발자도 이 위험을 이미 인지**

## 4. 이 코드베이스의 관례 (중요)

형제 도구들의 설명문에 컬럼 위치가 **하드코딩**되어 있다:
- `gaegeolmu-tracking`: "택배발송 파일(**B열**=운송장, **C열**=이름) → DeliveryList(**AA열**=이름, **E열**=운송장)"
- `tomato-tracking`: "제이비티 회신 파일의 운송장번호와 택배사(**K열**)"

→ goguma 파서도 **위치 기반 하드코딩**일 가능성이 높다. 그렇다면 헤더 이름만 고쳐서는 안 되고 값을 기대 위치로 옮겨야 한다.

## 5. 판별 테스트 (헤더 vs 위치)

P1 → `운송장번호`, Q1 → `택배사`로 헤더만 바꾼 파일을 업로드:
- **성공** → 파서는 헤더 기반. 근본 수정 = 별칭 사전에 한진양식 헤더 추가.
- **동일 실패** → 파서는 위치 기반. 정상 동작했던 해달 발주서 원본 1건을 확보해 기대 레이아웃을 특정해야 함.

## 6. 권장 수정 (소스 확보 후)

1. **양식 자동 판별**: 헤더명이 아니라 *값의 형태*로 운송장 컬럼 탐지 — 데이터 행의 8~14자리 숫자가 가장 많이 채워진 열 선택. 한진/CJ/롯데 양식이 바뀌어도 안 깨짐.
2. **헤더 별칭 사전**: `운송장번호|송장번호|운송장|invoice|tracking|지불조건(한진양식 오용)` 매핑 테이블화.
3. **발주서 생성 시 주문번호를 메모2(T열)에 각인** → 왕복 매칭을 이름+전화 추측에서 **주문번호 정확 일치**로 승격. 이게 동명이인 문제의 유일한 근본 해결책.
4. **에러 메시지 개선**: "찾을 수 없습니다"만 던지지 말고 *읽어들인 헤더 목록 + 숫자열 후보*를 함께 반환. 지금은 사용자가 원인을 알 방법이 전혀 없다.
